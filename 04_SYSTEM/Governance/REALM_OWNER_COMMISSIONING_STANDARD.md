# OLYMPUS REALM OWNER COMMISSIONING STANDARD

**Status:** Canonical reusable commissioning procedure
**Authority:** Human Owner → Zeus
**Applies to:** Persistent Olympus Realm Owner Gods

## 1. Purpose

This standard defines how Olympus creates, provisions, validates, and commissions a persistent Realm Owner without copying another God's identity, lifecycle, memory, or specialist Skill set.

Prometheus-agent / LAB is the first validated reference case. Future Gods reuse the anatomy and process, not Prometheus' personality or Realm lifecycle.

## 2. Initiative front door

Every new Initiative receives one lightweight first-pass review from Zeus before normal Hermes-agent orchestration.

Zeus records a concise briefing covering:
- understood goal and desired outcome;
- material boundaries and constraints;
- obvious governance, authority, or policy implications;
- likely Realm impact;
- major risks or irreversible consequences;
- whether a persistent Agent, Realm, system component, or sovereign decision may be implicated.

If no sovereign work is required, Zeus passes the briefing to Hermes-agent. Zeus does not become the Initiative's routine operator.

## 3. Hermes operational assessment

Hermes-agent deepens the operational analysis:
- required capabilities;
- accountable Realm Owner;
- supporting Realm Owners;
- suitable Skills and Tools;
- temporary-worker needs;
- context and permission requirements;
- execution dependencies and handoffs.

Hermes-agent prefers existing Agents, peer collaboration, shared Skills, and Temporary Workers before recommending another persistent God.

## 4. Persistent-God justification

If existing capability is insufficient, Hermes-agent returns an **Agent Creation Context** to Zeus containing:
- capability/ownership gap;
- evidence that the need is durable rather than task-specific;
- why an existing Agent, team, Skill, Tool, or Temporary Worker is insufficient;
- likely Realm and operating scope;
- expected peer collaborations;
- technical/runtime constraints;
- risks and expected complexity;
- Hermes-agent recommendation.

Hermes-agent does not define the new God's sovereign identity or authority.

## 5. Zeus God Blueprint

Zeus owns the Blueprint. Each Blueprint must define:

1. Identity
   - technical identifier
   - display identity
   - mythological identity/archetype
   - Realm
   - role
2. Soul
   - temperament
   - thinking style
   - default behavior
   - values/principles
   - uncertainty posture
   - collaboration posture
   - failure posture
3. Mission
4. Responsibilities
5. Explicit non-responsibilities
6. Authority and approval boundaries
7. Initiative ownership rules
8. Capabilities
9. Initial Skill set
10. Skill evolution / trusted Skill Pool policy
11. Tools and permissions
12. Context policy
13. Agent Memory policy
14. Mnemosyne / Librarian access
15. Peer collaboration model
16. Hermes-agent relationship and escalation
17. Temporary Worker / delegation policy
18. Realm lifecycle
19. Quality bar
20. Observability / reporting
21. Failure and recovery behavior
22. Commissioning tests

## 6. Human Owner identity checkpoint

Before provisioning, the Human Owner must have a clear opportunity to review the material **Who am I?** choices: Identity, Soul, mission, Realm, responsibilities, non-responsibilities, and authority boundaries.

Zeus may propose these from the Greek identity and Realm purpose, but must not silently freeze material identity choices when Human input is required.

## 7. Canonical contract versus runtime projection

The repository Blueprint/Agent contract is the canonical definition of the God. Hermes-agent then projects the authorized design into the supported runtime profile.

Typical projection:

```text
Canonical Blueprint / Agent Contract
        ↓
SOUL.md / runtime identity
role instructions / profile context
config.yaml / enabled toolsets
curated Skills
Tools + permissions
context policy
Agent Memory configuration
```

Do not treat runtime files as a competing source of truth. Do not omit Soul/identity from runtime merely because it exists in the Blueprint.

## 8. Skill commissioning policy

A new God receives a curated initial Skill set appropriate to the Realm. The initial set is a baseline, not a permanent ceiling.

After commissioning:
- if a new recurring capability belongs to the God's Realm, the God may re-consult the trusted Skill Pool and propose/request a suitable Skill;
- if the need primarily belongs to another Realm, prefer peer collaboration instead of duplicating that Realm's specialist Skills;
- shared procedures should remain reusable/shared where possible;
- Skill availability, assignment, default loading, Tool authority, and action authority remain separate.

Skill installation or permission expansion must follow the applicable provenance, security, authorization, and technical-verification rules.

## 9. Collaboration and escalation

Realm Owners are peers. They may communicate directly for capability discovery, bounded collaboration, artifact handoffs, and domain consultation.

Hermes-agent retains responsibility for Initiative routing, team composition, accountability coordination, ownership disputes, and material handoffs. Hermes-agent does not need to relay every peer message.

Normal escalation:

```text
Operational / routing / ownership → Hermes-agent
Sovereign / governance / constitutional → Hermes-agent → Zeus
Direct Realm Owner → Zeus → exceptional only
```

## 10. Communication observability

Where implemented, Agent-to-Agent communication uses the Olympus Communication Layer V1:

1. Agent Message
2. Conversation / Thread
3. Console Mirror
4. Structured Event Log
5. Initiative Correlation
6. Audit / Replay

Preserve provenance and operational correlation. Conversation logs are not automatically Agent Memory and are not canonical Mnemosyne knowledge.

## 11. Provisioning

After Blueprint authorization, Hermes-agent provisions exactly the authorized design. If implementation constraints conflict with the Blueprint, Hermes-agent returns the conflict to Zeus. It must not silently weaken boundaries or redesign the God.

Provisioning should record:
- profile/runtime created or changed;
- runtime identity/Soul projection;
- Skills assigned;
- Tools enabled/disabled;
- permission boundaries and whether they are technically enforced or behavioral only;
- memory configuration;
- context-loading behavior;
- known implementation limitations.

## 12. First awakening and 'Who am I?' validation

The candidate's first commissioning interaction validates identity before ordinary task competence.

Zeus asks the candidate to establish, in its own words:
- Who are you?
- What Realm do you own?
- Why do you exist?
- How do you think and behave?
- What outcomes are you accountable for?
- What are you explicitly not responsible for?
- What may you decide?
- What requires Human approval?
- What goes to Hermes-agent?
- What reaches Zeus?
- How do you work with peer Realm Owners?
- What is your Agent Memory?
- What is Mnemosyne?
- How may your Skill set evolve?

A concise mythological/storytelling framing is allowed and encouraged when useful, but the answers must map to the authorized Blueprint rather than inventing new authority.

## 13. Fresh-session commissioning

After identity validation, test the candidate in a fresh session against its actual runtime configuration. Validate identity, ownership, boundaries, Skills/Tools, memory separation, collaboration, escalation, Realm lifecycle, permissions, and failure behavior.

Zeus then commissions, revises, or rejects the candidate.

## 14. Post-commissioning evolution

Commissioning does not freeze the God forever. Operational experience belongs first to Agent Memory. Reusable procedural improvements may become Skills. Reusable curated knowledge may be proposed through Librarian-agent to Mnemosyne. Material identity, Realm, authority, lifecycle, or constitutional changes return to Zeus governance.
