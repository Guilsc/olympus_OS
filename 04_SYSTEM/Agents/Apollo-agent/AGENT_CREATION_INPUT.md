# APOLLO-AGENT / WORK — GOD CREATION INITIATIVE

**Status:** READY FOR ZEUS INTAKE  
**Target branch:** `feature/apollo-agent-work`  
**Target Agent:** `Apollo-agent`  
**Target Realm:** WORK  
**Authority:** Human Owner → Zeus  
**Execution:** Zeus designs and authorizes; Hermes-agent provisions; candidate is validated and commissioned.

## 1. Objective

Create and commission **Apollo-agent**, the persistent Realm Owner for **WORK**, using the current Olympus Realm Owner commissioning standard.

This is the second God-creation cycle after Prometheus-agent / LAB.

Do not copy Prometheus' Soul, lifecycle, permissions, or Skill set. Reuse the commissioning anatomy and process, then deliberately design Apollo for WORK.

## 2. Operating instruction

Run the God Creation Loop end-to-end.

Do not add a separate pre-review gate merely because Apollo is the next implementation. Let the flow expose real issues.

When an implementation, governance, runtime, Skill, permission, memory, collaboration, or commissioning problem is discovered:

1. identify the actual failure or mismatch;
2. route it through the existing Zeus ↔ Hermes loop according to authority;
3. correct the relevant design, provisioning instruction, or reusable commissioning standard when the lesson is genuinely reusable;
4. preserve provenance and distinguish Apollo-specific fixes from system-wide lessons;
5. continue the commissioning flow from the appropriate checkpoint;
6. do not silently work around constraints.

Escalate to the Human Owner only when a material Human decision, explicit approval boundary, or unresolved sovereign choice is genuinely required.

The goal is for the commissioning process to **learn from execution**, not to simulate completeness in advance.

## 3. Required starting flow

```text
New Initiative
→ Zeus first-pass institutional review
→ Hermes-agent operational capability / implementation assessment
→ Zeus designs Apollo-agent Blueprint
→ Human Owner resolves material identity / authority choices when required
→ Hermes-agent provisions the authorized candidate
→ Zeus performs identity / "Who am I?" awakening
→ fresh-session validation against actual runtime
→ Zeus commissions / revises / rejects
```

Zeus should begin by framing:

- why WORK needs a persistent Realm Owner;
- the intended outcome of Apollo-agent;
- the boundary between WORK and LAB / STUDIES / PERSONAL / AUTOMATIONS;
- the WORK-specific ownership model;
- material governance and authority concerns;
- what should be delegated to Hermes-agent for operational assessment;
- what must remain a Zeus decision.

Zeus should stay at the architecture / governance layer and avoid becoming Apollo's routine operator.

## 6. Identity and Soul requirement

Apollo must receive a real runtime identity, not only a repository description.

The Blueprint is canonical. Hermes-agent must project the approved identity into supported runtime mechanisms such as:

- `SOUL.md`
- role instructions / profile context
- profile metadata
- curated Skills
- Tools and permissions
- context policy
- memory configuration

Do not repeat the Zeus gap where the runtime Soul remains generic while identity exists only in project instructions.

## 7. "Who am I?" awakening

Before ordinary capability testing, Zeus should validate Apollo's identity.

The candidate should be able to answer in its own words:

- Who am I?
- What is WORK?
- Why do I exist?
- How do I think and behave?
- What outcomes do I own?
- What am I explicitly not responsible for?
- What may I decide?
- What requires Human approval?
- What do I escalate to Hermes-agent?
- What, exceptionally, reaches Zeus?
- How do I work with peer Realm Owners?
- What is my Agent Memory?
- What is Mnemosyne?
- How may my Skill set evolve?

A concise mythological/storytelling framing is welcome if it improves identity coherence, but it must map to the authorized Blueprint and must not invent authority.

## 8. WORK-specific design

Do not reuse LAB's lifecycle.

Design a WORK lifecycle around professional outcomes such as:

- projects and deliverables;
- business analysis;
- product / process / solution work;
- professional research;
- reports and presentations;
- professional sites / applications;
- coordination and delivery;
- professional content and visual deliverables when WORK owns the outcome.

The lifecycle should distinguish intake, accepted Initiative ownership, active delivery, blocked/on-hold behavior where useful, completion, archive, and handoff.

Use the smallest useful model. Do not add ceremony just for symmetry with LAB.

## 9. Skill architecture

Apollo receives a curated initial WORK Skill set from the trusted Olympus Skill Pool.

Rules:

- initial Skills are a baseline, not a permanent ceiling;
- Apollo may re-consult the trusted Skill Pool later when a demonstrated capability need belongs to WORK;
- when a need primarily belongs to STUDIES, PERSONAL, AUTOMATIONS, or LAB, prefer collaboration with the relevant Realm Owner rather than duplicating all of that Realm's specialist Skills;
- reusable procedures may be shared across Realm Owners;
- Skill availability, assignment, default loading, Tool access, and action authority remain separate;
- inspect provenance, security, dependencies, runtime availability, and permissions before assignment or installation.

Use the existing Skill architecture/audit artifacts as evidence. Do not assume Zeus' broad inventory should be copied into Apollo.

## 10. Cross-Realm collaboration

Apollo is a peer Realm Owner.

Apollo may communicate directly with other Realm Owners for:

- capability discovery;
- bounded contribution requests;
- artifact/interface clarification;
- consultation;
- cross-Realm execution collaboration.

Hermes-agent remains responsible for:

- team composition;
- Initiative routing;
- accountable ownership;
- material handoffs;
- cross-Realm conflicts;
- operational escalation.

Direct peer communication does not transfer Initiative accountability.

Normal sovereign escalation is:

```text
Apollo-agent → Hermes-agent → Zeus
```

Direct Apollo-agent → Zeus should be exceptional.

## 11. Communication observability

If inter-Agent communication is exercised during Apollo commissioning, align it with Olympus Communication Layer V1:

1. Agent Message
2. Conversation / Thread
3. Console Mirror
4. Structured Event Log
5. Initiative Correlation
6. Audit / Replay

Do not add external transport adapters or a dedicated chat surface in this cycle.

Conversation logs are operational/audit records. They do not automatically become Agent Memory or Mnemosyne knowledge.

## 12. Memory and knowledge

Preserve the three-layer separation:

```text
Working Context = what this task needs now
Agent Memory    = what Apollo has experienced
Mnemosyne       = what Olympus knows
```

Apollo may retain Agent-specific operational lessons in its isolated Agent Memory.

Reusable canonical knowledge must follow the governed knowledge path through Librarian-agent / Mnemosyne when that implementation exists. Do not convert conversations or Agent Memory into canonical knowledge automatically.

## 13. Learning loop

Treat this Apollo cycle as the first live use of the revised commissioning standard after Prometheus.

If the process fails or exposes ambiguity:

- fix the Apollo-specific contract if the issue is Apollo-specific;
- update `REALM_OWNER_COMMISSIONING_STANDARD.md` only when the lesson is reusable for future Gods;
- update architecture/principles only when the lesson changes Olympus-wide behavior;
- preserve historical commissioning evidence rather than rewriting past facts;
- continue until Apollo is either commissioned or a real Human decision blocks progress.

Do not stop merely to produce a review report.
